# AI Agent向け EZ Sign NFC プロトコル仕様化ガイド

**目的:** 公式アプリの通信キャプチャと実機再生試験から、AI Agentが再現可能なプロトコル仕様書を作るための手順・証拠モデル・テンプレート。

## 結論

- 既知の基準は **RC-S300 + EZ Sign 2.9インチ2色**。公開writerはUSBキャプチャからAPDUを抽出し、`F0 D3`画像チャンクを再生する。
- `F0 D8 / F0 D3 / F0 D4 / F0 DE` は重要な候補だが、役割は4.2インチ実機キャプチャで確定する。
- 4.2インチでは、解像度・色数・RF給電・更新時間・チャンク数を2.9インチから推測しない。
- 最初にやるべきことは、公式Windowsアプリ + RC-S300で4.2インチの白/黒/特色/パターンをキャプチャし、2.9インチと比較すること。

## 調査の進め方：手元の機材から仕様書完成まで

以下は今後実施する調査手順であり、実機試験の完了報告ではない。公式アプリとRC-S300で正解となる通信を確保し、同じ装置で再現した後、画像生成を進める。2.9インチ実機がなければ、4.2インチ単体の調査を先行する。

### 全体の流れと判断基準

| 段階 | 実施内容 | 残すもの | 次へ進む条件 |
|---|---|---|---|
| 0. 準備 | 対象機種・アプリ・機材を特定 | 環境記録、接続写真 | 対象の色数・型番と公式更新経路が分かる |
| 1. 基準動作 | 公式アプリで既知画像を更新 | 成功動画、元画像、操作記録 | 実機が安定して更新できる |
| 2. 採取 | RC-S300のUSB通信を保存 | 生pcapng、時刻付き結果 | 開始前から表示完了後まで取得できる |
| 3. 復元 | 要求・応答を対応付け、層を分ける | 全APDU時系列、証拠台帳 | パケット番号まで遡れる |
| 4. 再生 | 同じ装置・RC-S300で送信列を再現 | 再生ログ、画面写真 | 異なる画像へ繰り返し更新できる |
| 5. 解読 | 画像の差分と通信の差分を比較 | フィールド仮説、符号化候補 | 未使用画像でも予測が成立する |
| 6. 仕様化 | シーケンス・応答・制約を整理 | 仕様書v0.1、テストベクタ | 既知画像を独立実装で再現できる |
| 7. 無人試験 | 固定設置で再更新・復旧を試す | 成功率、所要時間、復旧結果 | 想定運用条件で反復更新できる |

### 0. 対象と機材を固定する

人が実機の型番・色数・寸法表記を確認し、Agentが環境記録を作る。4.2インチ・4色という前提は現物で確認する。公式アプリのOS・版、PCのOS・リーダードライバ版、RC-S300の識別情報も記録する。

公式アプリがWindows版でRC-S300を利用できるか、最初に確認する。Android版しかない場合はWindows版の利用可否を先に調べる。その経路が使えなければAndroid側で取得可能なアプリログ等の範囲を評価し、RC-S300を用いた公式通信取得は未実施と記す。

### 1. 公式アプリで成功条件を作る

白一色と黒一色を交互に表示し、配置を固定して数回更新する。元画像、公式アプリのプレビュー、更新前後の写真を保存する。送信開始、アプリの完了表示、電子ペーパーの表示安定の各時刻を分けて記録する。

失敗する場合はアンテナ位置、接触距離、公式アプリ設定を調整して基準動作を作る。公式アプリでも不安定な状態では、後の失敗をプロトコルの誤りと判定できない。

### 2. RC-S300で通信を採る

1. RC-S300を接続し、Wireshark/USBPcapで対応するUSBバス・デバイスを特定する。
2. 更新操作の前からキャプチャを開始する。接続・初期化も含める。
3. 公式アプリで画像を1回更新する。
4. アプリの完了表示と実際の表示安定を確認してから停止する。
5. 1実行1ファイルで保存し、実験IDを元画像・写真・操作メモにも付ける。
6. 同じ画像を複数回取得し、画像と無関係に変わるカウンタやセッション情報を探す。

USBキャプチャはPCとリーダー間の観測であり、RF波形や給電状態の直接測定ではない。USBログだけで「RF fieldが継続していた」と断定しない。採取方法の出発点は[参照writerのREADME](https://github.com/hijimasa/EZ-Sign-nfc-unofficial-writer/blob/main/README.md)にある。

保存単位の例（まだ取得していないファイルの構成案）：

~~~text
experiments/CAP-001/
  environment.json     # 型番、版、配置、入力、操作条件
  input.png            # 公式アプリへ渡した原本
  capture.pcapng       # 改変しない生ログ
  apdu.jsonl           # 解析で復元した要求・応答
  result.jpg           # 更新後の画面
  notes.md             # 操作時刻、所要時間、成功/失敗
~~~

### 3. 全通信を復元してからコマンドを分類する

AgentはUSB転送の方向・長さ・識別子から要求と応答を対応付ける。転送の分割と再組立て、送信要求と完了イベントの重複を確認し、単なるバイト検索で同じAPDUを二重計上しない。F0 D3だけでなく、その前後の初期化・終了処理・待ち時間も保持する。

APDU一覧には、実験ID、送受信時刻、元pcapngのパケット番号、全要求、全応答、通信エラー、暫定的な層分類を記録する。リーダー制御・カード向けAPDU・分類不能を分け、FFで始まるという理由だけで除外しない。SWとして解釈するのはカード応答部分を特定した後にする。

抽出スクリプトの結果とWireshark上の先頭・途中・末尾を照合する。不明な包み方や欠落があれば、仕様推定より先に抽出処理を修正する。

### 4. まず既知画像をそのまま再生する

対象装置の公式キャプチャを元に、同じRC-S300で初期化・画像送信・終了処理を再現する。最初は元の順序と待ち時間を保ち、2.9インチwriterの固定初期化列を4.2インチへ無条件に適用しない。

白→黒→白など、実際に画面変化が分かる順で試す。全応答が正常でも、画面が更新されなければ成功としない。失敗したら最初に公式ログと違う位置へ戻り、応答、送信長、初期状態、間隔を比較する。中断後の途中チャンク再送は、再送可能性が確認されるまで採用しない。

この段階で分かるのは「既知列を再生できる」ことであり、「任意画像を符号化できる」ことではない。

### 5. 差分実験で画像形式を解く

一度に一つの条件を変える。Agentは各仮説について、どの入力なら候補を区別できるかを提案し、人が公式アプリでその入力を送る。

| 入力の組み合わせ | 調べる内容 |
|---|---|
| 同一画像を繰り返す | セッション依存値、カウンタ、時刻等の有無 |
| 白・黒・各対応色の単色 | 色の符号、色プレーン候補 |
| 左右半分・上下半分 | 走査方向、行列の順序 |
| 非対称の角マーク | 回転、反転、原点 |
| 1画素/8画素幅の線、隣接位置の点 | ビット順、パッキング、境界 |
| 単純柄と複雑柄 | 圧縮や可変長化の可能性 |
| 同じ柄を別モデルへ送る（所有している場合） | モデル依存ヘッダやサイズ差 |

公式アプリによる拡大縮小・回転・ディザリングの影響を記録する。意図した1画素がアプリ内で変換されていれば、通信の差分をそのまま画素位置と解釈しない。

ヘッダ、圧縮、パディングの可能性を残し、データ長が画素数と近いだけでraw framebufferと断定しない。仮説確定には、解析に使わなかった非対称画像などで予測と実表示が一致することを求める。

### 6. 仕様書を段階的に完成させる

最初に「既知列再生仕様v0.1」を作り、対応モデル、完全な送受信列、待機、完了条件、未知フィールドを記す。画像符号化が解けたら「任意画像生成仕様」へ進める。未解読の部分は不透明なデータとして保持し、任意画像対応済みと表記しない。

各コマンドにはoffset、長さ、観測値、意味の候補、適用モデル、証拠IDを付ける。仕様書の記述から生成したデータを別の実装で送信し、元の公式キャプチャを丸ごと再生せずに表示できるか確認する。

欠落・重複・順序変更などの異常系は正常再生が安定した後、毎回既知の初期状態から一条件ずつ試す。未知の設定フィールドを網羅的に書き換える必要はない。失敗応答と復旧経路が分かる範囲で試験を止める。

### 7. 固定したままの無人更新を試す

表示器を取り外さず、異なる画像を一定間隔で送る。更新ごとの接続・切断・再検出の条件を記録する。成功数/試行数、転送時間、表示完了までの時間、最初に失敗した処理、復旧方法を集計する。

更新完了を確認してから次の更新へ進み、まず少数回で動作を確認する。その後、想定する更新間隔で試行数を増やす。再起動後、通信失敗後、ネットワーク再接続後にも動作するか確認してから、クラウド取得と定期実行を組み込む。画面消灯中の動作とOSサスペンドからの復帰は別試験として扱う。

### 人とAgentの分担・毎回の引き継ぎ

人は機材接続、公式アプリ操作、位置調整、目視確認を担当する。Agentは入力パターン作成、ログ解析、差分比較、仮説管理、再生コード作成、仕様書更新を担当する。Agentに実機アクセスがなければ、接続や表示成功を推測で報告しない。

1回の調査の終わりに「実験ID／変更条件／観測結果／支持・反証された仮説／未解決点／次の1実験」を残す。毎回、生ログと仕様書の証拠参照を対応付ける。

最初の引き継ぎセットは、対象機種とアプリ版の記録、白・黒それぞれの元画像と成功キャプチャ、更新後写真、操作時刻で十分。これをAgentへ渡し、まず全送受信列と差分一覧を生成させる。

## 証拠ラベル

| ラベル | 意味 | 仕様書での扱い |
|---|---|---|
| OBSERVED | キャプチャ・ログ・一次資料・実機で直接確認 | 断定可。証拠ID必須 |
| REPRODUCED | 別実行でも再現 | 手順・期待応答必須 |
| INFERRED | 観測からの合理的推定 | 推定と反証条件を明記 |
| UNKNOWN | 未観測 | 値を埋めず次実験を書く |
| CONFLICTING | 条件によって不一致 | 条件分岐で保存 |

## 既知の候補

| 項目 | 現状 |
|---|---|
| 画像送信 | 独自 `F0 D3` APDU。複数チャンクに分割される |
| 表示パラメータ候補 | `F0 D8 00 00 05 00 00 00 00 0E` は2.9インチ例として報告。4.2インチ値は未確定 |
| NDEF選択候補 | `00 A4 04 00 07 D2 76 00 00 85 01 01`。実機応答を証拠化 |
| リーダー依存候補 | `FF 5C / FF 5D`。EZ Sign本体APDUと分離して扱う |
| 成功応答 | 公開writerは `90 00` を正常扱い。ただし画面更新まで確認する |

## 4.2インチ比較キャプチャ

1. `42-white`: 白一色
2. `42-black`: 黒一色
3. `42-red`: 特色/赤など
4. `42-pattern`: 4×4、縦横ストライプ
5. `29-vs-42`: 同じパターンで2.9と4.2を比較

差分として見るもの: `F0 D8`、ヘッダ、解像度、色プレーン、`F0 D3`総数、チャンク番号、`Lc`、`F0 DE`、完了時間。

## Agentプロンプト

~~~text
あなたはNFC機器のプロトコルリバースエンジニアである。公式アプリのキャプチャと実機再生から、第三者が実装できる仕様書を作れ。

必須:
- 全主張に OBSERVED / REPRODUCED / INFERRED / UNKNOWN / CONFLICTING を付ける。
- 変化実験または一次資料なしにバイト列の意味を断定しない。
- RC-S300制御とEZ Sign本体APDUを分離する。
- 2.9/4.2、2色/4色を混同しない。
- 成功判定をSW=9000だけにせず、最終チャンク、完了応答、画面更新、再接続まで含める。
- 各フィールドにoffset、length、encoding、observed values、confidence、evidence IDsを書く。
- UNKNOWNは空欄にせず、最小の次実験を書く。
- 再現テストベクタと失敗診断表を出す。
~~~

## 次の実験優先順位

- **P0:** 4.2インチ基準キャプチャ、2.9 vs 4.2差分、APDU再生。
- **P1:** 欠落/重複/順序変更、Android IsoDep。
- **P2:** アンテナ位置、距離、電圧、温度、長期連続更新。

## ハードウェア評価

| 構成 | 強み | 主な未解決点 |
|---|---|---|
| Android専用端末 | NFC、電池、Wi-Fi/LTE、OTAを一体化。IsoDep API | Activity/Doze、固定位置、端末差 |
| Linux化スマホ | systemdで無人常駐・再起動が素直 | 機種依存NFCドライバ、サスペンド復帰 |
| RC-S300 | 現時点の基準リーダー | 大型、USB依存、固有制御の分離 |

## 品質ゲート

- すべての断定に証拠IDまたは一次資料URLがある
- モデル・色数・解像度・リーダー条件が明記されている
- F0 D3の総チャンク数、チャンク番号、Lc、ペイロード長が整合する
- 成功・失敗・タイムアウト・離脱・再接続が記述されている
- 公式キャプチャの再生結果と画面結果が一致する
- 4.2インチ未取得の値を推測で埋めていない
